### Decisions made

1. **Popup re-sync choice (3.4):** on open the control renders from ACTUAL `getEnabledRulesets()` state; if `actual !== stored intent`, it silently re-syncs by **sending the intent through the SW** (`toggleBlocking{enabled:intent}`), then renders that ack's effective value. Rationale: extension-shell makes durable **intent** the source of truth and mandates re-derivation after update/reload — so we correct the transient effective layer toward intent, never overwrite intent with the effective state. Divergence should be rare (SW `onInstalled`/`onStartup` already re-apply), this is a belt-and-braces reconcile. If the re-sync ack fails, the honest ACTUAL state is left displayed (no guess). If intent is unreadable but ground truth read succeeds, ACTUAL is still displayed without a re-sync.
2. **ACK effective value:** on `{ok:true}` the SW reports `enabled` (== what it forced into DNR); the popup always renders the ack's value, never the requested one, per contract. Because `applyBlockingState` returns `enabled` only after the storage set + (conditional) update resolve, `{ok:true}` is a confirmed-application signal; any throw rejects the chain link ⇒ `{ok:false, error}`.
3. **Chain rejection neutralization:** `applyBlockingState` prepends `.catch(() => undefined)` before `.then(...)` so a single failed application (e.g. transient DNR/storage error) cannot poison the shared `applying` chain and strand later intents. Still serializes and "last intent wins". Documented here as an intentional robustness addition over the literal design pseudocode.
4. **Constants** `STORAGE_KEY="blockingEnabled"`, `RULESET_ID="ad_rules"`, `TOGGLE_TYPE="toggleBlocking"` duplicated in both files as literals (no shared module — MV3 classic scripts, no import in service-worker context per eslint `sourceType: "script"`).
