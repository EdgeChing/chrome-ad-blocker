## Exploration: 一个 Chrome 广告拦截插件，Manifest V3，用 declarativeNetRequest 做规则拦截，带一个可以开关拦截的 popup

### Current State

Greenfield — the project directory contains no code, only SDD scaffolding (`openspec/config.yaml`, empty `specs/` and `changes/archive/`). There is no existing architecture to preserve; this change defines it.

The authoritative design reference (`D:\Cash Project\test\chrome-ad-blocker-plugin-plan.txt`) describes a dual-layer ad blocker (network DNR + DOM cleanup) with a 4-phase MVP roadmap. **Scope mapping:** the user's requested scope (MV3 skeleton + DNR rule blocking + popup on/off toggle) corresponds to **design-doc Phase 1 minus the basic DOM-hide layer, plus a simplified global toggle** (the doc defers per-site toggles to its Phase 2 options page). The DOM cleanup layer (`content.js` + MutationObserver), remote list auto-update, and per-site whitelist are explicitly out of scope for this change.

Key technical facts were verified against the official Chrome `declarativeNetRequest` API reference (developer.chrome.com, page last updated 2026-05-05). Verified findings that shape the design:

1. **Three rule scopes with different persistence:**
   - *Static* rules live in JSON files declared under `declarative_net_request.rule_resources`; installed/updated with the extension package.
   - *Dynamic* rules (`updateDynamicRules`) persist across browser sessions **and** extension updates; atomic per call.
   - *Session* rules (`updateSessionRules`) are in-memory only — cleared when the browser shuts down or a new extension version is installed.
2. **Toggling off does NOT require removing block rules.** `RuleAction.type` includes `block`, `redirect`, `allow`, `upgradeScheme`, `modifyHeaders`, and `allowAllRequests`. At equal priority, actions order as `allow/allowAllRequests > block > upgradeScheme > redirect`, so a single high-priority session `allow` rule can override the whole block set (the uBlock-style pattern). Additionally:
   - `updateEnabledRulesets({disableRulesetIds / enableRulesetIds})` enables/disables **whole static rulesets** at runtime. The enabled-set state **persists across browser sessions but NOT across extension updates** — after an update, the manifest's `rule_resources[*].enabled` wins again.
   - `updateStaticRules()` can disable/enable individual static rule IDs (max 5000 disabled).
   - `getEnabledRulesets(): Promise<string[]>` exists to read back which rulesets are enabled.
3. **Current quotas (Chrome 120/121+, i.e., all modern Chrome):** up to 100 static rulesets in the manifest, ≤50 enabled at once (`MAX_NUMBER_OF_ENABLED_STATIC_RULESETS`), with a guaranteed minimum of **30,000 static rules** (`GUARANTEED_MINIMUM_STATIC_RULES`, shared globally across extensions beyond that — check `getAvailableStaticRuleCount()`); up to 5000 session rules; dynamic: 5000 "unsafe" floor + up to 30,000 safe rules on Chrome 121+ (`MAX_NUMBER_OF_DYNAMIC_RULES`); ≤1000 regex rules per rule type; each rule <2KB compiled. **There is no documented per-update-call rule-count cap** — updates are atomic and bounded only by the totals above.
4. **Rule conditions:** `urlFilter` uses Adblock-like pattern tokens (`||domain/`, `abc*d`, etc.). If a condition omits both `resourceTypes` and `excludedResourceTypes`, **all resource types except `main_frame` are blocked** — i.e., omitting it is the safe default (top-level navigation can't be broken). Valid `resourceTypes` strings include `main_frame`, `sub_frame`, `stylesheet`, `script`, `image`, `font`, `object`, `xmlhttprequest`, … (`"*"` is **not** a valid value — see divergences below).
5. **Permissions:** `"declarativeNetRequest"` (install-time warning, implicit host access for allow/block rules) vs `"declarativeNetAccessWithHosts"`-family name in current docs: `declarativeNetRequestWithHostAccess` (no install warning; requires prior host permission per host). For an all-sites blocker with `host_permissions: ["<all_urls>"]`, plain `"declarativeNetRequest"` is the standard, simplest choice.
6. **MV3 service-worker lifecycle** (well known, matches config.yaml + design doc): SW can be killed at any time (~30s idle); no persistent in-memory state; `chrome.storage.local` is the durable store; `onInstalled(reason)` and `chrome.runtime.onStartup` are the wake/re-sync points.
7. **Known DNR limitation:** rules don't affect responses generated by a *page's own* service worker or its CacheStorage (only requests reaching Chrome's network stack, including HTTP cache). Edge case for SPA-heavy sites; acceptable.

**Divergences between the design doc and current docs** (flagged per project convention — do NOT silently override; none block this change):
- D1: Doc says "batch updates to respect DNR quotas (~512 rules/update)" and "300k conditions total". The current reference documents no 512-per-call cap and the totals above instead. Impact: negligible for MVP (≤ ~500 static rules); Phase 2 remote-list planning should use the corrected numbers. Batching large updates remains good practice for performance, not a documented hard limit.
- D2: Doc's example rule uses `"resourceTypes": ["*"]` — `*` is not a valid `ResourceType` value; such a static rule would be **silently ignored in packed extensions**. Use the omitted form (blocks everything except `main_frame`) or an explicit enum list instead.
- D3: Doc's manifest example points the ruleset at `_locales/rules.json` — that directory is for i18n messages; use a normal path like `rules.json`.

### Affected Areas

All files are new (greenfield). Minimal viable file set:

- `manifest.json` (new) — MV3 skeleton: `permissions: ["declarativeNetRequest", "storage"]`, `host_permissions: ["<all_urls>"]`, `background.service_worker`, `action.default_popup`, and the static ruleset declaration. No `tabs` permission needed for this scope (the doc's manifest includes it for later phases — dropping it is a deliberate minimization, not a conflict).
- `rules.json` (new) — packaged DNR ruleset: JSON array of Rule objects (`id` number + optional explicit `priority`, `condition.urlFilter` per ad domain, `action.type: "block"`, resourceTypes omitted = safe default). Seed scale ~50–500 domains.
- `background.js` (new) — service worker: single source-of-truth sync between `chrome.storage.local` (`blockingEnabled`) and DNR state; idempotent apply on `onInstalled` (all reasons) + `onStartup`; message handler for the popup toggle. No in-memory state that matters after the call returns.
- `popup/popup.html`, `popup/popup.css`, `popup/popup.js` (new) — small UI: one switch reflecting current state; on change, writes storage and messages the SW (or vice versa per Decision C).
- Optional: `icons/` (16/48/128 PNGs) for store-readiness; not functionally required.

Explicitly NOT in this change: `content.js`, `hide.css`, options page, remote list fetcher, filter parser — all belong to later phases per the design doc roadmap.

### Approaches

The core decision is **where blocking rules live and how the on/off toggle interacts with DNR**. Three viable approaches (state persistence in `chrome.storage.local` + SW re-sync applies to all three):

1. **Static ruleset + `updateEnabledRulesets()` global toggle** — Rules ship in packaged `rules.json`; toggling off calls `updateEnabledRulesets({disableRulesetIds:["ad_rules"]})`, on re-enables it; state mirrored in `chrome.storage.local`.
   - Pros: zero quota churn (no rule add/remove per toggle); minimal code; static rules are held by the browser regardless of SW liveness (most robust against MV3 SW kills); immediate effect, no reload; `getEnabledRulesets()` allows state reconciliation.
   - Cons: enabled-set resets to manifest default on every extension update → must re-apply from storage in `onInstalled(reason:"update")` (small, deterministic step, but a real failure mode if forgotten — toggle silently flips back ON after updates/dev reloads); rule *content* changes require repackaging (fine for MVP; remote lists come later anyway); granularity is whole-set only.
   - Effort: Low

2. **Dynamic rules pushed via `updateDynamicRules()` + remove/re-add on toggle** — the design doc's background-driven pipeline; toggling off removes all rule IDs, on re-adds them.
   - Pros: matches the design doc's architecture; natural foundation for Phase 2 (remote lists → dynamic rules); per-rule granularity available now.
   - Cons: every toggle = ~1000 atomic rule operations (two calls) — wasteful and a brief window where rapid toggling can race; more code paths to test; dynamic rules persist across sessions/updates so no re-push is needed on restart, but the install-time push must be correct or blocking silently doesn't start.
   - Effort: Medium

3. **Base block set (static or dynamic) + session `allow`/`allowAllRequests` override rule** — uBlock-style: toggling off adds one high-priority session rule that allows everything; on removes it. Works regardless of where the base rules live.
   - Pros: 1-rule update per toggle; decouples toggle from base-rules representation (future-proof for Phase 2); `allowAllRequests` even gives frame-hierarchy semantics for later per-site modes.
   - Cons: session rules vanish on browser shutdown and extension update → must re-apply from storage at **every** startup (`onStartup`) — more SW-lifecycle surface than approach 1; slightly harder to reason about (override rule interacting with base set).
   - Effort: Low–Medium

Supporting decisions (orthogonal to the above):

4. **MVP rule source/scale:** (a) hand-curated seed list of ~50–500 well-known global + Chinese ad/tracker domains as static JSON, vs (b) a local build-time script parsing EasyList / EasyList China / AdGuard lists into that same static JSON (no runtime networking). Both produce the same artifact shape; (a) is faster to ship, (b) gives real coverage. Recommend starting with (a) sized per design doc (~500), keep (b) as an option.
5. **resourceTypes strategy:** omit `resourceTypes` in block rules → DNR blocks all types except `main_frame` by default: simplest and safest; avoids the invalid `"*"` from the doc example. Blocking `script`/`xmlhttprequest` of ad domains can break pages that use those hosts for non-ad purposes — with no per-site whitelist in MVP scope, staying at the safe default is the conservative choice (open question for user).
6. **Popup ↔ SW communication:** (a) popup calls DNR/storage APIs directly; vs (b) popup only reads storage for initial UI and sends a message to the SW, which is the single writer of both `chrome.storage.local` and DNR state. Recommend (b): one invariant owner + idempotent `applyState()` keeps behavior identical whether the write came from the popup or from startup re-sync.
7. **DOM cleanup layer:** deferred by explicit user scope; network-layer blocking alone delivers the doc's Phase-1 core value, but cosmetic/in-page ads will remain visible until that layer ships — set expectations with the user (no technical blocker).

### Recommendation

**Approach 1 (static ruleset + `updateEnabledRulesets`) as the MVP toggle mechanism**, with approach 3 documented in the design doc as the extension path for per-site/per-frame "allow" modes once remote/dynamic rules land. Rationale: it minimizes moving parts and SW-lifecycle coupling, has zero quota churn, is held by the browser independent of SW liveness, and its one sharp edge (reset on extension update) is handled by a single idempotent re-sync call.

Target MVP shape for proposal/spec/design to build on:

- **Manifest:** `manifest_version: 3`; `permissions: ["declarativeNetRequest", "storage"]`; `host_permissions: ["<all_urls>"]`; `background.service_worker: "background.js"`; `action.default_popup: "popup/popup.html"`; `declarative_net_request.rule_resources: [{id:"ad_rules", enabled:true, path:"rules.json"}]`.
- **State model:** `chrome.storage.local` key e.g. `{blockingEnabled: boolean}` (default `true` on first install) is the single source of truth for *intent*. DNR state is a derived effect, re-derived idempotently by one function `applyBlockingState(enabled)` called from: popup toggle message → SW handler; `chrome.runtime.onInstalled` (covers `"install"`, `"update"` — mandatory because enabled-rulesets reset to manifest default on update); and defensively `onStartup`.
- **Toggle flow:** popup reads storage on open → renders switch; user flips → popup writes storage + sends `{type:"toggleBlocking", enabled}` message → SW validates, calls `updateEnabledRulesets`, confirms. (Design phase may allow the SW to own the storage write too; keep one writer.)
- **Rules file:** JSON array of block rules, one per domain: `{"id": n, "priority": 1, "action":{"type":"block"}, "condition":{"urlFilter":"||domain.example/"}}` — explicit `priority`, resourceTypes omitted (safe default). Seed ~50–500 domains incl. top Chinese ad networks (Alimama/阿里妈妈, Baidu Union/百度联盟, Tencent ads, etc.) since EasyList coverage there is weak per the design doc's own risk note.
- **Optional nicety:** `setExtensionActionOptions({showBadges:true})` gives a free block-count badge (persisted across sessions) — cheap differentiator, keep out of MVP unless trivial.

### Risks

- **Enabled-rulesets reset on extension update is documented Chrome behavior** — if the `onInstalled("update")` re-sync is missed or broken, the user's "off" toggle silently flips to ON after every store update / unpacked reload. This needs an explicit spec scenario + test (verify: install → disable → bump version/update → still disabled).
- **Design-doc quota figures are stale** ("~512 rules/update", "300k conditions") vs current documented limits — see divergences D1–D3 above. No impact on MVP scale; must not be copied into specs verbatim (specs/design should cite the corrected numbers or avoid specific caps).
- **Chinese ad-network coverage** is a real product risk, not just technical: generic EasyList under-covers CN sites (doc risk #4). If the target audience is primarily Chinese users, the seed list and later remote lists must include EasyList China / AdGuard Chinese filters; if global-first, weight accordingly. Needs user input (open question Q1).
- **False positives without a per-site whitelist:** blocking whole domains can break pages that use those hosts for non-ad content/CDN purposes; in MVP the only escape hatch is the global off switch. Acceptable trade-off to confirm with user (Q5), and it argues for keeping resourceTypes at the safe default initially.
- **SW lifecycle fragility** (doc risk #1, confirmed): any state kept in SW memory dies silently; all durable state must round-trip through `chrome.storage.local`. Also: a message sent to a dead SW wakes it — fine — but event-based re-sync points (`onInstalled`/`onStartup`) are the only reliable recovery paths.
- **DNR does not intercept responses from pages' own service workers / CacheStorage** (documented) — some SPA ads may slip through; cosmetic DOM layer (deferred) is the eventual mitigation, plus DNR still covers the network origin of most ad requests.
- **Global static rule quota is shared across all installed extensions** beyond the 30k guarantee (`getAvailableStaticRuleCount()`) — irrelevant at ~500 rules but worth a note for Phase 2 when remote lists push into thousands.
